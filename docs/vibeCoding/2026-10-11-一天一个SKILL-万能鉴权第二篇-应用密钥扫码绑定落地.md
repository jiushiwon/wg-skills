## 一、这次真正实现了什么？不是一句"支持扫码登录"

### 1. 四张表设计

```
┌──────────────┐     ┌──────────────┐
│  wg_sys_app  │────>│ wg_sys_app_key │
│   (应用)      │     │   (密钥)       │
└──────────────┘     └──────────────┘
        │
        ▼
┌──────────────────────┐
│  wg_sys_app_binding │
│    (用户绑定关系)     │
└──────────────────────┘
        │
        ▼
┌──────────────────────┐
│   wg_sys_bind_code  │
│     (绑定码)         │
└──────────────────────┘
```

### 2. 两种身份

| 身份类型 | 说明 | 示例 |
|----------|------|------|
| **宿主身份** | 统一账户体系的真实用户 | `wg_sys_user.id = 10086` |
| **应用身份** | 第三方平台的用户标识 | 小程序 `openid`、App `user_id` |

### 3. 两条绑定链路

- **宿主发起**：Web 端生码 → 小程序扫码确认
- **应用发起**：老项目申请码 → 用户去统一账户确认

## 二、应用表：先分清"谁在接入"

`wg_sys_app` 代表一个接入系统。

```sql
CREATE TABLE wg_sys_app (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    app_name VARCHAR(100) NOT COMMENT '应用名称',
    app_key VARCHAR(64) UNIQUE NOT COMMENT '公开应用标识',
    owner_id BIGINT NOT COMMENT '所属用户ID',
    description VARCHAR(255) COMMENT '应用描述',
    callback_url VARCHAR(255) COMMENT '回调地址',
    status TINYINT DEFAULT 1 COMMENT '状态 1:正常 2:禁用',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

**常见错误**：把 `appKey` 和 `appSecret` 都塞在应用表里。

**正确做法**：应用只是"项目是什么"，密钥才是"项目怎样证明自己"。

## 三、应用密钥表：密钥必须能轮换

`wg_sys_app_key` 管 `apiKey + apiSecret`。

```sql
CREATE TABLE wg_sys_app_key (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    app_id BIGINT NOT COMMENT '所属应用ID',
    api_key VARCHAR(64) UNIQUE NOT COMMENT '密钥ID',
    api_secret VARCHAR(128) NOT COMMENT '密钥密文',
    status TINYINT DEFAULT 1 COMMENT '状态 1:正常 2:禁用',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_app_id (app_id)
);
```

**核心设计点**：

1. **一对多**：一个应用可以有多组密钥
2. **可轮换**：旧密钥泄露 → 禁用 → 创建新密钥
3. **一次性返回**：`apiSecret` 只在创建时返回一次，之后不再展示

### 签名验证原理

```java
// 小程序后端调用开放接口
public class AppSignatureVerifier {

    public static String sign(String queryString, String apiSecret) {
        // 签名原文 = 查询字符串 + api_secret
        String signStr = queryString + "&api_secret=" + apiSecret;
        return HmacSHA256(signStr, apiSecret);
    }

    public static boolean verify(SignRequest request, String apiSecret) {
        String expected = sign(request.getQueryString(), apiSecret);
        // 常量时间比较，防止时序攻击
        return MessageDigest.isEqual(
            expected.getBytes(),
            request.getSignature().getBytes()
        );
    }
}
```

**请求头格式**：

```http
X-App-Key: ak_xxx        -- 密钥ID
X-Timestamp: 1704067200  -- 秒级时间戳
X-Nonce: random_string    -- 随机串
X-Signature: HmacSHA256签名结果
```

**服务端验证**：

1. 根据 `X-App-Key` 查询密钥
2. 校验时间戳（300秒内有效）
3. 验证签名
4. 验证通过 → 获取应用信息 → 允许调用

## 四、绑定关系表：两个系统的用户如何认成同一个人

`wg_sys_app_binding` 是这套体系的核心。

```sql
CREATE TABLE wg_sys_app_binding (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT COMMENT '宿主用户ID',
    app_id BIGINT NOT COMMENT '所属应用ID',
    app_user_id VARCHAR(128) COMMENT '应用侧用户ID',
    bind_type VARCHAR(20) COMMENT '绑定类型: wechat/phone/google',
    unionid VARCHAR(128) COMMENT '微信unionid',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_app_user (app_id, app_user_id),
    INDEX idx_user_id (user_id)
);
```

**绑定关系示例**：

| user_id | app_id | app_user_id | bind_type |
|---------|--------|-------------|-----------|
| 10086 | 1 | oWx_123456 | wechat |
| 10086 | 2 | 13800138000 | phone |

**核心原则**：
- 用稳定的应用侧用户 ID，不是会变化的昵称/手机号
- 不是把第三方资料搬到中枢，而是建立映射关系

## 五、绑定码表：二维码背后必须有一次性凭证

扫码不是扫到一个 URL 就直接绑定，必须有一次性的绑定码。

```sql
CREATE TABLE wg_sys_bind_code (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    code VARCHAR(64) UNIQUE NOT COMMENT '绑定码',
    user_id BIGINT COMMENT '宿主用户ID(宿主发起时)',
    app_id BIGINT NOT COMMENT '所属应用ID',
    bind_type VARCHAR(20) COMMENT '绑定类型',
    bind_direction VARCHAR(20) COMMENT '绑定方向: user_initiated/app_initiated',
    expires_at DATETIME NOT COMMENT '过期时间',
    status TINYINT DEFAULT 0 COMMENT '状态 0:待使用 1:已使用 2:已失效',
    used_at DATETIME COMMENT '使用时间',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_code (code),
    INDEX idx_expires (expires_at)
);
```

**状态流转**：

```
待使用(0) ── 成功消费 ──> 已使用(1)
   │
   └── 超时或主动失效 ───> 已失效(2)
```

### 并发防重复：条件更新

```sql
UPDATE wg_sys_bind_code
SET status = 1, used_at = NOW()
WHERE code = ? AND status = 0 AND expires_at > NOW();
```

**关键点**：
- 带状态条件更新：`status = 0`
- 检查过期时间：`expires_at > NOW()`
- 受影响行数 = 1 才算成功
- 并发下只有一个请求能绑定成功

## 六、案例一：小程序扫码，把已有 Web 账户绑定进来

**场景**：张三已经登录了 Web 账户中心，想把微信小程序也接进来。

### 完整流程

```
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│  Web端      │         │  统一账户   │         │  小程序     │
│ (发起绑定)  │         │   (中枢)    │         │  (扫码)    │
└──────┬──────┘         └──────┬──────┘         └──────┬──────┘
       │                         │                         │
       │ 1.生成分享码            │                         │
       ├──────────────────────> │                         │
       │                         │                         │
       │ 2.返回绑定码+二维码     │                         │
       │ <──────────────────────┤                         │
       │                         │                         │
       │                         │ 3.用户扫码              │
       │                         │ <────────────────────── │
       │                         │                         │
       │                         │ 4.返回绑定页面          │
       │                         │ ─────────────────────> │
       │                         │                         │
       │                         │ 5.用户确认              │
       │                         │ <────────────────────── │
       │                         │                         │
       │                         │ 6.写入绑定关系          │
       │                         │ ✓                      │
       │                         │                         │
       │ 7.轮询/推送看到成功     │                         │
       │ <──────────────────────┤                         │
```

### 核心接口

```java
// 1. Web端：生成分享码
POST /api/bind/code
{
    "appId": 1,           // 小程序应用ID
    "bindType": "wechat"  // 绑定类型
}
// 返回: { "code": "ABC123", "expiresIn": 300 }

// 2. 小程序：获取绑定信息
GET /api/bind/info/{code}

// 3. 小程序：确认绑定（需微信授权获取用户信息）
POST /api/open/bind/claim
{
    "code": "ABC123",
    "wechatCode": "微信授权码"
}

// 4. Web端：轮询绑定状态
GET /api/bind/status/{code}
// 返回: { "status": "pending" | "confirmed" | "expired" }
```

## 七、案例二：老项目先有用户，用户主动来绑定统一账户

**场景**：写作平台运行两年，有老用户，不想立刻迁移到新账户体系。

### 完整流程

```
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│  写作平台   │         │  统一账户   │         │  用户       │
│  (老项目)   │         │   (中枢)    │         │            │
└──────┬──────┘         └──────┬──────┘         └──────┬──────┘
       │                         │                         │
       │ 1.用户点击"绑定统一账户" │                         │
       │ <──────────────────────┤                         │
       │                         │                         │
       │ 2.申请绑定码            │                         │
       │ ─────────────────────> │                         │
       │                         │                         │
       │ 3.返回绑定码            │                         │
       │ <──────────────────────┤                         │
       │                         │                         │
       │ 4.跳转统一账户中心       │                         │
       │ ─────────────────────────────────────────────> │
       │                         │                         │
       │                         │ 5.用户确认绑定          │
       │                         │ <────────────────────── │
       │                         │                         │
       │                         │ 6.写入绑定关系          │
       │                         │ ✓                      │
       │                         │                         │
       │ 7.跳转回写作平台         │                         │
       │ <─────────────────────────────────────────────┤ │
```

### 核心接口

```java
// 1. 老项目：申请绑定码
POST /api/open/bind/apply
{
    "appId": 1,
    "appUserId": "writer_u_9527"  // 写作平台用户ID
}
// 返回: { "code": "XYZ789", "bindUrl": "https://auth.xxx.com/bind/xyz" }

// 2. 统一账户：用户确认
POST /api/bind/confirm
{
    "code": "XYZ789"
}

// 3. 老项目：查询绑定状态
GET /api/open/bind/status?appUserId=writer_u_9527

// 4. 老项目：通过appUserId获取宿主用户信息
GET /api/open/user/info?appUserId=writer_u_9527
```

**重要意义**：老项目不需要立刻删表、迁库、改密码体系，只需要用户愿意时增加一条映射。

## 八、安全边界：这些我们刻意没做

### 1. 不让接入项目再存密码

接入方可以有自己的业务表，但不能再复制用户密码、JWT 签发、角色表。

### 2. 不把业务私有资料塞进账户中枢

| 公共资料 | 私有资料（业务方保留） |
|----------|----------------------|
| 用户名 | 订单记录 |
| 头像 | 文章/内容 |
| 手机号 | 健康数据 |
| 邮箱 | 支付信息 |

**原则**：统一身份 ≠ 拿到 ID 就能获取一切。身份识别和数据授权是两件事。

### 3. AI 不能拿用户身份乱操作

- ✅ AI 可以读接口契约
- ✅ AI 可以生成接入代码
- ✅ AI 可以用被授权的应用身份做有限调用
- ❌ AI 不能创建密钥
- ❌ AI 不能删除应用
- ❌ AI 不能解绑账户

**原则**：AI 能提高接入速度，不能变成绕过安全边界的理由。

## 十、总结

这期我们落地了：

1. **四张核心表**：应用、应用密钥、绑定关系、绑定码
2. **两种身份**：宿主身份 + 应用身份
3. **两条绑定链路**：宿主发起 + 应用发起
4. **签名验证机制**：HMAC-SHA256 + 时间戳防重放

**核心理念**：万能鉴权不是"所有项目共用一张用户表"，而是让所有项目拥有一个可信的"同一个人"身份锚点。
