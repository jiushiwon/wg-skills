# JWT 与登录态令牌

## 一、算法选型

| 情况 | 用 | 理由 |
|---|---|---|
| 单服务自签自发 | **HS256** | 签发方和验证方是同一个服务，共享密钥即可，最简单 |
| 多服务互验 | **RS256 / ES256 / EdDSA** | 验证方只拿公钥就能验，私钥只留在签发方 |
| 需要第三方验证 | RS256 / EdDSA | 同上，公钥可公开分发 |
| 前后端分离但同一家公司 | HS256 即可 | 前端不校验签名，只解码 payload |

**真正要禁的不是 HS256**，而是：

- `alg: none` —— 攻击者去掉签名段就能伪造任意 payload。服务端必须**固定期望算法**，绝不读 header 里的 `alg` 决定验签方式。
- 短密钥 —— HS256 密钥至少 256 位（32 字节）。启动时校验长度，不达标直接失败退出。
- 把密钥写进代码或提交进仓库。

## 二、令牌结构

```
header.payload.signature
```

Base64Url 编码的 JSON，段之间用 `.` 连接。

```json
{ "alg": "HS256", "typ": "JWT" }
{ "sub": "user_id", "exp": 1735689600, "iat": 1735686000, "jti": "唯一ID" }
```

常用载荷字段：

| 字段 | 含义 |
|------|------|
| `sub` | 主体（用户 ID） |
| `exp` | 过期时间（秒级时间戳） |
| `iat` | 签发时间 |
| `nbf` | 生效时间 |
| `jti` | 令牌唯一 ID，**用于登出黑名单/刷新令牌复用检测** |
| `iss` | 签发者 |
| `aud` | 受众 |

> JWT 载荷是**编码不是加密**，任何人都能 Base64Url 解开看内容。别放密码、身份证、密钥。

## 三、双令牌

| 令牌 | 有效期 | 存储位置 | 用途 |
|------|--------|----------|------|
| Access Token | 短（15~60 分钟） | 内存（前端） | 每次请求携带 |
| Refresh Token | 长（7~30 天） | HttpOnly + Secure Cookie 或服务端存储 | 换新的 Access Token |

要点：

- Access Token 短命，减少泄露窗口。
- Refresh Token 必须能撤销（服务端存哈希 + `jti` 黑名单）。
- **Refresh Token 轮换**：每次刷新发新令牌、旧令牌标记失效；检测到旧令牌被复用说明泄露，直接吊销整条链。
- 登出：Access Token 短命自然过期，Refresh Token 立即作废。

## 四、密钥轮换

生产环境 JWT 密钥不能永不变。用 `kid`（key id）写在 header 里，服务端维护 `kid → 密钥` 映射：

```json
{ "alg": "HS256", "kid": "2026-01", "typ": "JWT" }
```

轮换时新旧密钥并存一段时间（密钥集合），验证时按 `kid` 选密钥；找不到 `kid` 才回退到当前密钥。这样不用强制踢掉所有人下线。

## 五、验证顺序

1. 从 `Authorization: Bearer <token>` 取令牌。
2. **固定算法**验签（不读 header 的 alg）。
3. 校验 `exp` / `nbf` / `iss` / `aud`。
4. 查 `jti` 是否在黑名单。
5. 全通过才进入业务。

任何一步失败都返回同一个错误码，不要告诉调用方"是签名错了"还是"是过期了"。

## 六、常见错误

```python
# 错：按 header 里的 alg 决定验签方式 → alg:none 攻击
if token.header["alg"] == "HS256": ...

# 错：用 == 比较签名 → 时序攻击
if computed_sig == token.signature: ...

# 错：不校验 exp
claims = decode(token)   # 只解码不验证签名，等于没鉴权

# 错：密钥硬编码
JWT_SECRET = "wg-skills-secret"
```
