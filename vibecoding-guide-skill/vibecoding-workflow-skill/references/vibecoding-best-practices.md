# VibeCoding 最佳实践

一句话：高效与 AI 协作开发产品的经验总结。

## 1. 任务拆分原则

AI 一次做不好大事。把任务拆到足够小：

| 不好的任务 | 好的任务 |
|------------|----------|
| "帮我做个商城" | "帮我设计用户系统的接口" |
| "优化这个项目" | "把 `src/utils/date.ts` 里的日期格式化函数重构一下" |
| "写个登录页面" | "写一个 Vue 登录表单组件，包含手机号、验证码、提交按钮" |

## 2. 上下文给足

每次让 AI 写代码前，至少提供：

- 项目技术栈
- 相关文件路径
- 接口契约或数据结构
- 不能改动的约束
- 期望的输出格式

## 3. 先方案后代码

不确定时，先让 AI 给方案：

```text
先不要写代码，告诉我实现这个功能的 2-3 种方案，并比较优缺点。
```

方案确认后再让它写代码，避免反复修改。

## 4. 小步验证

AI 生成的代码不要一次性合并，要：

1. 先生成一个函数/组件
2. 跑通测试
3. 再生成下一个
4. 每一步都 review

## 5. 用 AI 审查 AI

让 AI 帮你 review 它自己写的代码：

```text
请审查这段代码，找出潜在 bug、性能问题和安全隐患。
```

## 6. 保留人工决策点

以下地方不要完全交给 AI：

- 数据库 Schema 设计
- 安全策略（鉴权、加密）
- 支付/资金相关逻辑
- 架构重大变更

## 7. 命名和注释

让 AI 生成代码时要求：

- 命名清晰（不要 a/b/c）
- 复杂逻辑加注释
- 不要过度注释 obvious 代码

## 8. 版本控制

VibeCoding 也要遵循版本控制：

- 每个功能一个 commit
- 不要一次性提交大量 AI 生成代码
- commit message 写清楚改动内容
- 重要改动先建分支

## 9. 测试策略

- 核心路径必须有测试
- 用 AI 生成测试，但必须人工检查
- 不要追求 100% 覆盖率

## 10. 成本控制

- 优先用本地模型做简单任务
- 复杂推理再用 Claude 4 / GPT-4o
- 监控 AI API 调用量和费用
- 缓存重复请求

## 反模式清单

| 反模式 | 后果 |
|--------|------|
| 完全相信 AI 代码 | 引入 bug、安全漏洞 |
| 一次让 AI 做太多 | 质量下降、难定位问题 |
| 不给上下文 | AI 乱猜、代码不符合项目风格 |
| 不 review 就合并 | 技术债快速累积 |
| 忽视测试 | 回归 bug 多 |
| 过度优化 | 浪费时间和 token |
